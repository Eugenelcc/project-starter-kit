An engineered process for building with an AI pair.

A free set of project documents and Claude Code agents for any stack. Every task is one file, tests come first, and you sign off at every gate that matters.

Use the template Open the playground

Fig. 0 — why it exists

An AI pair is fast. It also guesses, forgets and wanders.

The kit fixes that with plain Markdown files and three rules. It works for a web app, a bot, an API, anything. The worked example is Spendlygo, a Telegram expense tracker built this way.

rule 01

Decisions live in files

What to build, the hard rules and every task's plan are written down, not lost in a chat.

rule 02

Humans hold the gates

The owner approves the requirements, the plan and the merge. Claude never passes a gate alone.

rule 03

Never assume

Unsure? Claude asks: a plain-language scenario first, then the detail, then options with pros and cons.

Fig. 1 — the pipeline

Eight stages, three human gates

  1. 0

    Intake

    The request becomes a B-### backlog item with one feature ID.

  2. 1

    Requirements ✋ owner

    Grilling first, then Given / When / Then criteria.

  3. 2

    Build plan ✋ owner

    Files, data, a test per criterion, risks, PR split.

  4. 3

    Tests first

    One failing test per criterion, before any code.

  5. 4

    Build

    Code until green. Never loosen a test.

  6. 5

    Review ✋ merge

    Agent review, then the owner merges. Claude never merges.

  7. 6

    Release

    Deploy and smoke-test. Broken? Revert first.

  8. 7

    Close

    Docs current, risks tested, deployed: Done.

opus: spec-planner · challenger · reviewer sonnet: test-writer · builder owner gate

Small-fix lane. About 30 lines or fewer, with no schema, dependency, API or high-risk change? Stages 1 and 2 may be skipped. Tests and review still run. If in doubt, it isn't a small fix.

Two strikes. After two honest failed attempts at the same problem, Claude stops and reports what failed, what it tried and the options.

Fig. 2 — one file per task

Every handoff is a file, never a conversation

A subagent starts with no memory of your chat. It gets one path, reads the file, and writes back only its own section. Context survives across agents, sessions and people.

  2. ## Requirements — whatspec-planner · opus
  3. ## Build plan — howspec-planner · opus
  4. ## Second opinionchallenger · opus · risky only
  5. ## Test reporttest-writer → builder · sonnet

  7. ## Reviewreviewer · opus

Fig. 3 — model routing

Opus thinks. Sonnet does. You decide.

Who · modelJob
Main session
orchestrator		Talks to the owner, grills them, records approvals, launches each agent. The only one who talks to the owner.
spec-planner
Opus		Writes the Requirements and Build plan. Never writes code.
challenger
Opus		An independent second opinion, written without seeing the conversation. Used for schema changes, money maths, auth, data deletion or a new external service.
test-writer
Sonnet		Turns acceptance criteria into failing tests.
builder
Sonnet		Implements the plan until the tests pass. Hands back to the planner if the plan doesn't fit the code.
reviewer
Opus		Checks the diff against the spec and guardrails, then gives a verdict: ready for owner, back to build, or back to plan.

Subagents never ask the owner directly. They write their questions into the spec file, and the main session relays them.

Fig. 7 — start a project

From template to first task

  1. Open the template repository and click Use this template → Create a new repository.
  2. Delete site/, kit/, .github/workflows/pages.yml and .github/workflows/release.yml. They only publish this page and the kit's releases and task files. Keep .kit-version.
  3. Replace the README with your own project's.
  4. Fill in PRD → Guardrails → CLAUDE.md → Design (if you have screens) → Backlog. Each file starts with guidance and links to Spendlygo's version.
  5. List your high-risk areas in Guardrails §8: where a bug would be silent and expensive.
  6. Write one CI script that both you and GitHub Actions run, and put its command into WORKFLOW.md and the agents.
  7. Add B-001 and tell Claude Code: "Let's start B-001. Follow WORKFLOW.md."

The setup checklist in the playground tracks these steps for you.

Fig. 8 — glossary

Glossary

Owner
The human who decides. They approve requirements, plans and merges.
Grilling
Rounds of short, plain-language questions Claude asks before writing anything, each with options and their pros and cons.
Acceptance criterion
One testable statement of correct behaviour, in Given / When / Then form.
Spec file
The single Markdown file per task that every agent reads and writes.
Subagent
A separate Claude Code worker with its own model, tools and instructions, in .claude/agents/.
Feature ID
F1, F2…: a feature's permanent name in the PRD.
B-###
A backlog item's permanent ID. One branch and one spec file per item.
High-risk areas
Where bugs are silent and costly. They never change without tests.
Small-fix lane
The shortcut for tiny, low-risk changes: skips requirements and planning, never tests or review.
Gate ✋
A point where the pipeline waits for the owner's explicit "approved".
Revert first
When production breaks, restore the last good version before investigating.
