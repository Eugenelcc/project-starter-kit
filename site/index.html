Why it exists

An AI pair programmer is fast, but it fills gaps with guesses, forgets everything between sessions, and will happily build things nobody asked for. This kit solves that with plain Markdown files:

  • Written decisions. What to build, the hard rules, and every task's plan live in files, not in a chat that disappears.
  • Human gates. The owner approves the requirements, the plan and the merge. Claude never passes a gate alone.
  • Never assume. When Claude is unsure, it asks: first a plain-language scenario, then the technical detail, then options with pros and cons.

It works for a web app, a bot, an API, anything. The worked example is Spendlygo, a Telegram expense tracker built this way. Every template links to Spendlygo's real, filled-in version.

The documents and where they live

PRD

PRD.md

What to build and why. Features get IDs (F1, F2…) that every branch, commit and PR cites. It also lists what's deferred, so scope can't creep.

Guardrails

GUARDRAILS.md

The hard rules, tagged 🔴 NEVER, 🟡 ASK FIRST or 🟢 ALWAYS. They cover cost, data, auth, secrets, privacy, scope, git, the testing floor, and when to stop and ask.

Design

DESIGN.md · optional

For projects with screens only: colour tokens, type, spacing, motion, components and copy, so every screen stays consistent.

CLAUDE.md

CLAUDE.md + one per area

A short operating manual. The root file loads into every session and subagent, so it stays small. Detail for one area goes in a nested CLAUDE.md that loads only when Claude works there.

The pipeline

Every task moves through the same eight stages. ✋ owner marks a human gate.

  1. Intake

    The request becomes a B-### item in the backlog, mapped to exactly one feature ID. If it conflicts with the guardrails, Claude stops and asks.

  2. Requirements: what ✋ owner

    Grilling first: rounds of up to four questions, until nothing material is unclear. Then the acceptance criteria, written as Given / When / Then, plus edge cases and what's out of scope.

  3. Build plan: how ✋ owner

    The files to change, any data changes, which test proves each criterion, the risks and the PR split. Risky items also get an independent second opinion.

  4. Tests, written first

    One failing test per acceptance criterion, written before any feature code. A test that passes before the build proves nothing.

  5. Build

    Code until the tests pass, following the plan exactly. Never loosen a test to get green; side ideas get parked.

  6. Review ✋ owner merges

    An agent reviews the diff against the spec and guardrails. Then Claude opens the PR, but only when the owner asks, and never merges it.

  7. Release

    Deploy and smoke-test using the runbook. If it breaks: revert first, fix second.

  8. Close

    Move the item to Done. It's done only when the docs are updated, the high-risk areas are tested, and the change is deployed and checked.

Small-fix lane. A change of about 30 lines or fewer, with no schema, dependency, API or high-risk change, may skip stages 1 and 2. It still gets tests and review. If in doubt, it isn't a small fix.

Two strikes. After two honest failed attempts at the same problem, Claude stops and reports what failed, what it tried and the options.

One file per task

Each task has a single file, docs/specs/B-###-<slug>.md, and every agent writes only its own section:

Grilling recapmain session, confirmed by owner
Requirements (what)spec-planner
Build plan (how)spec-planner
Second opinionchallenger, risky items only
Test reporttest-writer, then builder
Build notesbuilder
Reviewreviewer

Why one file? A subagent starts with no memory of your conversation. It gets only the file's path, reads it, and writes its result back. Every handoff is a file, never a conversation, so context survives across agents, sessions and people.

Who does what: model routing

Expensive judgement goes to the strongest model; executing a fixed plan goes to a faster one. Opus thinks, Sonnet does.

Who · modelJob
Main session
orchestrator		Talks to the owner, grills them, records approvals, launches each agent. The only one who talks to the owner.
spec-planner
Opus		Writes the Requirements and Build plan. Never writes code.
challenger
Opus		An independent second opinion, written without seeing the conversation. Used for schema changes, money maths, auth, data deletion or a new external service.
test-writer
Sonnet		Turns acceptance criteria into failing tests.
builder
Sonnet		Implements the plan until the tests pass. Hands back to the planner if the plan doesn't fit the code.
reviewer
Opus		Checks the diff against the spec and guardrails, then gives a verdict: ready for owner, back to build, or back to plan.

Subagents never ask the owner directly. They write their questions into the spec file, and the main session relays them.

How it maps to industry standards

Nothing here is new. The kit combines well-known practices into a form an AI agent can follow.

StandardWhere it lives here

Start a new project with this kit

  1. Open the template repository, click Use this template → Create a new repository, and name your project.
  2. In your new repo, delete site/ and .github/workflows/pages.yml. They only publish this page.
  3. Replace the README with your own project's.
  4. Fill in the documents in this order: PRD → Guardrails → CLAUDE.md → Design (if you have screens) → Backlog. Each file starts with a guidance comment and links to Spendlygo's version. Replace every <placeholder>.
  5. List your project's high-risk areas in Guardrails §8: the places where a bug would be silent and expensive (money, dates, permissions…).
  6. Pick your real test and CI commands, put them in one CI script that both you and GitHub Actions run, and put those commands into WORKFLOW.md and the agent files.
  7. Add B-001 to the backlog. In Claude Code, say: "Let's start B-001. Follow WORKFLOW.md." Then answer the grilling questions and approve each gate.

The whole kit costs nothing: plain Markdown, Claude Code's built-in subagents, and free GitHub Pages for public repositories.

Glossary

Owner
The human who decides. They approve requirements, plans and merges.
Grilling
Rounds of short, plain-language questions Claude asks before writing anything, each with options and their pros and cons.
Acceptance criterion
One testable statement of correct behaviour, in Given / When / Then form.
Spec file
The single Markdown file per task that every agent reads and writes.
Subagent
A separate Claude Code worker with its own model, tools and instructions, defined in .claude/agents/.
Feature ID
F1, F2…: a feature's permanent name in the PRD, cited everywhere.
B-###
A backlog item's permanent ID. One branch and one spec file per item.
High-risk areas
The parts of a project where bugs are silent and costly. They never change without tests.
Small-fix lane
The shortcut for tiny, low-risk changes that skips requirements and planning, but not tests or review.
Gate ✋
A point where the pipeline waits for the owner's explicit "approved".
Revert first
When production breaks, restore the last good version before investigating.
